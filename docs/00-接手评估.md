## 2. 项目本体

2 次提交：`17408a5` v1 主体 → `a58b197` 五篇 writeups。工作区有 2 个「改动」，见 §5 P0-3（**只是文件权限位，0 字节内容差异**）。

**架构主线**：先抽交付合同（specgen）→ 路由领域 skill（router）→ 早落第一版可打开交付物 → 每 2 步跑守卫（guard 把 `validate.py` 推进 task 容器执行）→ 3 次拒收后带 discrepancy 熔断收工。MCP 走同一个 WebSocket 循环，不是外挂工具。

| 文件 | 职责 |
|---|---|
| `submission.yaml` | name / model_api / install / serve / env，与官方示例几乎一致 |

| `skillkit/router.py` | 领域词表 + 路径家族标签 → `domain`（真实目录）/ `subdomain` |

## 5. 风险清单（按优先级）

### P0 — 决定「会不会拿 0 / 能不能提交」

1. **`serve.py` 心跳与官方协议冲突（最高优先）**。当前 `ping_interval=20, ping_timeout=60`；官方 `docs/protocol.md` 明确要求「Run your server without keepalive pings (`ping_interval=None`) or with a `ping_timeout` longer than your longest command」，而单条 `exec` 上限 600 s。长命令期间有被判断连、任务提前终止的风险（协议 §5：server 提前断开 = 该题算 harness 的 outcome）。**改法**：`websockets.serve(..., ping_interval=None)`。
2. **没有 `artifacts/`，从未跑 `kit check`**。`kit check` 的 artifacts 阶段与 `ready to submit` 都要求 29 题产物且已提交；这是 M1+M2 的全部工作量，也是当前唯一真正挡在提交前面的东西。
3. **工作区不干净**。`git status` 显示 `dryrun.py`、`serve.py` 为 `M`，diff 只有 `old mode 100755 → new mode 100644`（Windows 解压 + `.git/config` 里 `filemode = true` 造成，**内容零变化**）。官方 kit 的 `files` 阶段要求「entry is root of its own repository with everything committed」，并会保留 0755/0644 权限位。在 Linux 上用 `git update-index --chmod=+x serve.py dryrun.py` 恢复，或明确提交一次；别在 Windows 上让 git 改行尾。
4. **真模型端到端完全未验证**。writeups/04 自述：Anthropic 原生路径的 `tool_use` / `tool_result` 序列化与 `cache_control` 标记「只做了编译级验证，没有真跑过」。T-03 是最大未知数，且 `model_api` 与实际调用必须一致（违反即失格）。

### P1 — 合规与判据可信度

5. **F-01 公平规则灰区，提交前必须人工复核**。证据：
   - `skills/electrical/SKILL.md`、`skills/misc/SKILL.md` 的 frontmatter `covers:` 直接列出 dev task id；
   - `PLE_domain_skeleton.md` 含 baseline 的具体结论数值（如 `$1,309,439`、`0.8 MW`）与逐题交付路径；
   - `router.path_hint()` 用 workdir 路径里的家族标签（`final_batch4__electrical_task17__...`）加 +9 分，writeups/03 作者自己把它归为「灰区，但我认为合规」。
   官方规则禁止「hard-code task answers / fingerprint specific tasks」，且 dev-set 的 graders 与 reference files 公开但 harness 不得读取或使用。这些目前只作为文档与路由权重，不直接产出答案，**但会被评审人一眼看到**。建议：删掉 `covers` 里的 task id、把 skeleton 中的具体数值/结论从提交仓库移出（或明确标注为格式样本），保留一份「这些是格式惯例、不是答案」的合规说明。
6. **`criteria.py` 假阳性**。`g05/g06/g07` 用 `min(阈值, len(tasks))`：数据为 0 题时阈值退化为 0，`0/0` 判 PASS。作为「single source of truth」会在缺数据时给出错误的绿灯。修法：`len(tasks) < 29` 时直接 `BLOCKED`，不要用 `min`。同时 `INFO`（题面可读）目前被算作 A 层 FAIL，应单列为环境前置条件。
7. **`guard.py` 硬编码 `/tmp/ple_validate.py`、`/tmp/_v_*`** → dryrun 在 Windows 必失败（§4）。改用 `tempfile` 或写进 workdir，让 G-09 真正跨平台。
8. **模型调用参数偏保守**：`max_tokens=8000`（官方建议 Claude 给 32000）、非流式且 `httpx` 超时 600 s（官方建议流式或宽松超时；egress proxy 30 分钟无字节才断开）。Claude 默认最高 reasoning 可能让单步很慢，600 s 有超时风险；官方也明确「不要重试 400」——项目对 400 直接 raise，这点是对的。

### P2 — 提分项（README 已自述）

9. specgen 4 道无路径题（offset / footing / solar×2）只能给 `confidence=low`，靠首轮读 `task.md` 回灌；`task.md` 不在 workdir 根目录时失效。
10. guard 的 `zip_soft` 一律 WARN，未按题面措辞升级为硬判。
11. 「第 10~20 步落第一版」是从 84 步 baseline 反推的推断值，未用真模型校准。
12. **CRLF 风险**：kit 的 `files` 阶段要求 install/serve 脚本 LF 行尾（CRLF 会 warn）。本机 git 已提示「LF will be replaced by CRLF」，仓库没有 `.gitattributes`。建议加 `.gitattributes` 固定 `*.py text eol=lf`。
